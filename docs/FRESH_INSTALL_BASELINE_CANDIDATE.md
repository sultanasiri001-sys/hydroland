# Versioned fresh-install baseline candidate

The historical chain cannot initialize an empty database: the HR verification migration repeats an earlier column, foreign key and index definition. This candidate provides a separate, reviewable installation artifact without changing the historical files or claiming that historical replay succeeds.

## Contents and validation

`apps/api/prisma-fresh-install-candidate` contains a schema snapshot, one baseline migration and its SHA-256 component manifest. The baseline combines SQL generated by the locked Prisma tool from the canonical schema with the exact equipment, weather, messaging and append-only audit SQL components already exercised by the recovery rehearsal. It is not a snapshot of the production database.

`node apps/api/scripts/fresh-install-candidate.mjs --verify` is offline: it regenerates the reference and rejects any difference in schema, baseline SQL or component manifest. It connects to no database. `--write` prepares the candidate artifact; it does not deploy it. Published/approved baseline SQL must later remain immutable; future schema changes require additive migrations and reviewed transition tooling rather than automatic regeneration of an applied baseline. This initial candidate deliberately fails verification on canonical schema drift.

The recovery workflow runs two independent disposable PostgreSQL jobs. One exercises the generated reference; one actually deploys the stored candidate SQL. Both seed representative application relationships, verify operational extension contracts, back up and restore into two empty targets, compare complete schema/data/history, verify ORM reads and constraints, rerun deployment as a no-op, and detect deliberate data corruption. The candidate job records its actual one-entry baseline ledger; it does not fabricate the 78 historical entries.

A third independent job tests the versioned candidate followed by the two exact organization portal migrations from revision `e6efbf0c2b8c2de52bfcee85b8a3ec2e03259c5b` of #442. A separate checkout reads that immutable revision; the probe verifies its commit and both SQL hashes before application. The database contains a personal booking, payment/invoice and personal/organization customer cases before the forward deploy. It verifies preservation, new foreign keys, active personal/organization booking uniqueness, request-key uniqueness, cancelled history and incident linkage. The actual ledger has three entries, and both logical restores preserve the upgraded schema, all table data and that ledger. This tests these specific candidate SQL files on the canonical TEXT baseline; #442's independent four-type matrix covers TEXT/UUID forward migration variants. It does not certify a production upgrade or replace application authorization tests. New organization revisions require an explicit reviewed pin/hash update.

## Existing installations and release boundaries

Default production build/deploy commands still use the original migration path. No Render command or production database is changed. The only candidate database execution is inside the guarded, labelled loopback recovery container. This PR does not perform a baselining/resolve operation.

Before adoption: obtain the actual production schema and migration ledger, compare native types and all raw SQL objects, define reviewed empty-install and existing-install transitions with compatible future migration deployment, and test a real production backup plus provider PITR in isolated targets. Pending portal migrations must be incorporated as future additive changes, not silently lost when choosing this main-schema baseline. Issue #369 remains open. The versioned artifact and CI proof are implementation candidates, not approval for production deployment or a claim of complete historical recovery.
