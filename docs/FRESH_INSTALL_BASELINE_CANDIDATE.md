# Versioned fresh-install baseline candidate

The historical chain cannot initialize an empty database: the HR verification migration repeats an earlier column, foreign key and index definition. This candidate provides a separate, reviewable installation artifact without changing the historical files or claiming that historical replay succeeds.

## Contents and validation

`apps/api/prisma-fresh-install-candidate` contains a schema snapshot, one baseline migration and its SHA-256 component manifest. The baseline combines SQL generated by the locked Prisma tool from the canonical schema with the exact equipment, weather, messaging and append-only audit SQL components already exercised by the recovery rehearsal. It is not a snapshot of the production database.

`node apps/api/scripts/fresh-install-candidate.mjs --verify` is offline: it regenerates the reference and rejects any difference in schema, baseline SQL or component manifest. It connects to no database. `--write` prepares the candidate artifact; it does not deploy it. Published/approved baseline SQL must later remain immutable; future schema changes require additive migrations and reviewed transition tooling rather than automatic regeneration of an applied baseline. This initial candidate deliberately fails verification on canonical schema drift.

The recovery workflow runs three independent disposable PostgreSQL jobs. One exercises the generated reference, one deploys the stored candidate SQL, and one adds the organization migrations. All three seed representative application relationships, verify operational extension contracts, back up and restore into two empty targets, compare complete schema/data/history, verify ORM reads and constraints, rerun deployment as a no-op, and detect deliberate data corruption. The candidate job records its actual two-entry baseline/completion ledger; it does not fabricate the 78 historical entries.

A third independent job tests the versioned candidate followed by the two exact organization portal migrations from revision `e6efbf0c2b8c2de52bfcee85b8a3ec2e03259c5b` of #442. A separate checkout reads that immutable revision; the probe verifies its commit and both SQL hashes before application. The database contains a personal booking, payment/invoice and personal/organization customer cases before the forward deploy. It verifies preservation, new foreign keys, active personal/organization booking uniqueness, request-key uniqueness, cancelled history and incident linkage. The actual ledger has four entries, and both logical restores preserve the upgraded schema, all table data and that ledger. This tests these specific candidate SQL files on the canonical TEXT baseline; #442's independent four-type matrix covers TEXT/UUID forward migration variants. It does not certify a production upgrade or replace application authorization tests. New organization revisions require an explicit reviewed pin/hash update.

## Existing installations and release boundaries

Default production build/deploy commands still use the original migration path. No Render command or production database is changed. The only candidate database execution is inside the guarded, labelled loopback recovery container. This PR does not perform a baselining/resolve operation.

Before adoption: obtain the actual production schema and migration ledger, compare native types and all raw SQL objects, define reviewed empty-install and existing-install transitions with compatible future migration deployment, and test a real production backup plus provider PITR in isolated targets. Pending portal migrations must be incorporated as future additive changes, not silently lost when choosing this main-schema baseline. Issue #369 remains open. The versioned artifact and CI proof are implementation candidates, not approval for production deployment or a claim of complete historical recovery.

## Raw-domain coverage extension (2026-10-08)

A separate candidate migration restores the eight raw domains absent from the canonical 109-table rehearsal: ComplianceAssessment, ComplianceEvidence, TrainingCourse, WorkforceCenterDepartment, WorkforceDepartment, WorkforceHiringRequest, WorkforcePosition and WorkforceSeat. The captured production catalog contains schema metadata only (98 columns, 99 constraints including PostgreSQL 18 NOT NULL entries, 27 standalone indexes, nine enums). No production rows or credentials are included.

`node apps/api/scripts/raw-domain-completion.mjs --write|--verify` prepares or checks the deterministic SQL and checksum manifest. The original baseline remains unchanged. Internal UUID keys remain UUID; external foreign-key columns take the installed parent ID type, limited to TEXT or UUID. This is a new-installation adaptation, not a production ID conversion.

All three disposable recovery modes apply this additional real migration and compare columns, defaults, non-nullability, constraints, indexes and enum order with the captured catalog before dumping. Both complete restores compare the full database schema and ledger. Runtime HR/compliance workflows and production backup restoration are not certified by these schema checks. Matching table coverage does not establish complete production schema equivalence or authorize replacement of its historical migration ledger.


## Production column compatibility evidence

`production-column-reference.json` captures read-only metadata for all 117 production tables and 1186 columns on 2026-10-08. It includes no rows or credentials. Each recovery mode writes a separate sanitized `production-column-compatibility.json` report comparing every table and column name, native type, nullability and default expression against its actual installed candidate database. Missing production tables fail the coverage check; other differences remain explicitly reported and do not fail the synthetic restore test or imply production approval.

The comparator rejects duplicate metadata and distinguishes missing/extra columns even when totals match. Exact default-expression text may differ while meaning is equivalent; such entries need review. Constraints, indexes, triggers, functions, sequences and policies still require their own production comparison. Matching column metadata never authorizes ledger replacement or cutover. The next transition decision should use these concrete differences plus a real isolated production backup restoration, not infer compatibility from 117-table coverage.
