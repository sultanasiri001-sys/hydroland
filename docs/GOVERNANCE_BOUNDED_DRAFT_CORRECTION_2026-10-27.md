# Bounded textual draft correction

A newly queued draft may explicitly grant `ONE_DRAFT_REVISION_V1`. This optional checkbox starts unchecked. Omitting the grant preserves historical/default behavior and the existing request fingerprint. Changing the grant changes the fingerprint, so a reused request ID cannot silently change its authority.

Only EXECUTIVE, MARKETING, SALES, SUPPORT, INVENTORY and SOCIAL drafts using DRAFT_REPORT, DRAFT_MESSAGE or DRAFT_CAMPAIGN qualify. READ_OPERATIONS, human approval requests, governance reviews, legal and security execution agents are excluded. A valid RETURN_FOR_CORRECTION must contain findings, LOW or MEDIUM risk, no evidence gaps and no owner escalation. Prior reviews must retain valid immutable lineage and permit continuation.

Completion queues one new task for the original execution agent in the same transaction as the stop receipt. The original prompt, result, revision and all review rows remain unchanged. An append-only receipt pins the source and requesting review revisions. The new task receives the original brief, saved result and all preceding reviews plus the correction findings as untrusted input. It cannot broaden the brief, invent evidence, approve work, send messages or mutate business data. Before counting tokens or generating, the runtime checks current requester authority, the exact opt-in receipt, deterministic request key, unique correction link and immutable review chain. Invalid linkage fails closed.

The revised draft starts the six-review chain again. A second correction is never generated, even if a new grant is attached to the revised task. Neither the original file nor the revised file becomes approved. Successful final review produces only a recommendation requiring the owner's separate decision.

The original inbox file retains CORRECTION_REQUIRED and shows the linked revision state. A completed revision opens a separate read-only file with its own costs and six reviews. Invalid links expose no foreign task ID. The corrected file revalidates its original grant and stop-review lineage too; a corrupted original cannot leave the revision shown as ready for owner review. Fresh session/role checks, response identity validation and workspace fencing protect this navigation.

Paused agents retain the revision in QUEUED. The ordinary task reservation and daily cap still gate dispatch. A full/uninitialized execution queue records the deferral without losing the review. `POST /admin/agents/tasks/:id/draft-correction` can resume the already authorized one-round correction after capacity returns; it requires a current administrator and requester, expected review revision, reason and explicit acknowledgement. Concurrent requests return the same child task and create one resume receipt. This route cannot grant permission retroactively or retry an uncertain model request.

No schema migration, credential update, budget increase, production fixture or new paid model test is part of this change. Acceptance uses disposable PostgreSQL and a loopback provider for one-round eligibility, immutable source/reviews, exact provider context, six restarted reviews, legacy/evidence-gap/high-risk exclusions, stale and forged links, audit rollback, queue capacity, authority revocation and idempotent recovery. Browser coverage checks explicit consent, excluded scopes, malformed receipts, separate read-only files and fresh revocation.
